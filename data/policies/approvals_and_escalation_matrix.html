Approvals and Escalation Matrix (APR-01)

1. Purpose and How to Use This Matrix

This document consolidates every approval threshold and escalation trigger in the Northwind policy library into one place, with a pointer to the policy that owns each one. It exists so that a manager or employee can find out who approves something without knowing in advance which policy governs it.

1.1 This matrix is a map, not the territory

Every source policy governs its own rules. This matrix restates thresholds for navigation only. Where this document and a source policy differ, the source policy is correct and this one is out of date, and People Operations should be told so it can be fixed.

This is the one document in the library that deliberately repeats numbers defined elsewhere. Every other document cross-references rather than restating, precisely so that there is a single owner for each rule. Read an entry here, then read the source section before acting on anything consequential.

1.2 How to read an entry

Each row gives the situation, what approval is required, and the owning document and section. Where a row lists more than one approver, all of them are required unless the row says otherwise — approvals stack, they do not substitute.

1.3 The general rule on approvals

Three principles apply across every policy:

  • Approvals stack. A higher approval never replaces a lower one. Where a threshold requires a manager and a second approver, both must be recorded.
  • Nobody approves their own request, and nobody approves a request from which they personally benefit. Where the ordinary approver is conflicted, the request routes one level up.
  • A prohibition is not a high threshold. Some rules in this library cannot be approved by anyone at any level. These are marked PROHIBITED below, and there is no escalation route for them.

3.1 The trap in this table

Three separate rules can each block an international request independently: the country, the duration, and the notice. A request can fail all three at once, and none of them can be escalated. Managers should decline such requests directly rather than forwarding them for a decision nobody can make.

Note also that Canada and the United Kingdom are approved destinations under REM-01 but sit outside the US and EU for the purposes of the Restricted data rule in SEC-01. An employee whose role touches that data class can be approved to travel there and still be unable to do their job from there.

8. Escalation Paths and Edge Cases

8.1 When the approval chain terminates

Some employees have no manager recorded — the CEO by design. Where an approval chain has no next step, the request routes to People Operations, which records the approval. This is an expected condition with a defined route, not a data error to be escalated.

8.2 When the approver is conflicted

Nobody approves their own request, and nobody approves a request they benefit from. The request routes one level up, or to People Operations where there is no level up.

8.3 When no approver exists

For anything marked PROHIBITED in this matrix, there is no approver and no escalation path. Forwarding such a request upward wastes the requester's time and implies a possibility that does not exist. The correct response is to decline it, state which rule applies, and set out the alternatives that are available.

8.4 When two policies both apply

Where a situation touches more than one policy, every applicable requirement applies independently and the most restrictive governs. A trip that combines leave and work needs both a leave approval and a location approval, and neither implies the other. Approval under one policy never waives a requirement under another.

8.5 When a request is out of scope entirely

Where an employee asks about something no Northwind policy covers, the correct answer is that the policy library does not address it, and the question should be referred to People Operations. An absence of coverage is not an implied permission, and no approver should infer an entitlement from silence.

9. Document Control

9.1 Ownership

This matrix is owned by People Operations. Each underlying rule is owned by the policy in its source column, and changes are made there first. This document is updated to follow; it never leads.

9.2 Reporting an inconsistency

Anyone who finds a discrepancy between this matrix and a source policy should tell People Operations. Until it is corrected, follow the source policy.

9.3 Version and review

This is version v4.2, effective 2026-01-01. It supersedes all prior versions of the Northwind Approvals and Escalation Matrix. It is reviewed whenever any source policy changes and at least annually.
